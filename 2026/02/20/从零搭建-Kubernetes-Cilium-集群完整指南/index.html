0x01 系统准备（所有节点执行）

1.1 如何选择并配置虚拟机

本文选择 UTM 作为虚拟化方案，主要基于两点考虑：

  1. 开源免费：UTM 基于 QEMU，完全开源免费，无需担心许可证问题。而 VMware Fusion 虽然对个人用户免费，但商业使用仍需付费，且需要注册账号获取许可证，流程繁琐。
  2. 轻量易用：UTM 专为 macOS 设计，原生支持 Apple Silicon，安装即用，无需复杂配置。界面简洁直观，创建虚拟机只需几步操作。相比之下，VMware 体积庞大，功能繁多但对于搭建实验环境来说过于臃肿。

对于在 Mac 上搭建 Kubernetes 学习环境这类场景，UTM 完全够用，简单省心。执行下述命令即可下载：

1.2 如何关闭 Swap 分区

K8s 要求禁用 Swap 的原因是为了确保性能的确定性和资源调度的精确性，K8s 的设计哲学是：宁可让 Pod 因 OOM 快速崩溃并异地重启，也不允许因为磁盘交换而导致不可控的服务延迟。Swap 的介入会破坏 Cgroup 对容器内存的严格限制，导致调度器无法准确核算节点的真实负载。

相比之下，虚拟机默认开启 Swap 可以提高单机的鲁棒性，即：当内存突然不够用时，系统会用极慢的磁盘空间当临时内存顶上去，从而牺牲运行速度来换取不直接死机或重启。虚拟机可以正常运行过后，我们需要关闭 Swap 分区：

  1. 首先，执行下述命令，可临时关闭 Swap 分区，不必重启 reboot；

  2. 若要系统重启后，Swap 仍然是关闭状态，可执行下述命令，永久关闭 Swap 分区；

1.3 需要安装哪些基础依赖

系统出于安全考虑，在执行 sudo apt 时往往会丢弃当前用户的环境变量。因此，直接修改 apt.conf.d 配置专属代理文件可以绕过 sudo 的环境隔离，并提供持久化保障。

这样可以确保无论谁操作、是否重启，apt 都能稳定获取代理配置，避免了在特权模式下手动 export 变量失效或单次会话后消失的问题。给 apt 配置专属代理文件并非必须操作项，但下面安装基础依赖是必须操作项，否则无法下载对应的集群组件和工具。

0x02 安装 containerd（所有节点执行）

在构建 Kubernetes 集群时，选择合适的容器运行时（Container Runtime）是稳定性建设的第一步。

2.1 为什么选择 Docker 官方源

在 Ubuntu / Debian 软件源中，存在两个名称相似但维护主体完全不同的软件包：

  • 系统自带源 (containerd)：由发行版（如 Ubuntu）维护。为了追求极端的稳定性，版本通常非常保守。例如 Ubuntu 24.04 提供的 1.7.28 版本已接近该系列的生命周期终点；
  • Docker 官方源 (containerd.io)：由 Docker 公司维护的增强版，包含了最新的安全补丁、CRI 插件完整支持以及对 K8s 1.35+ 新特性（如cgroup v2 深度优化）的更好兼容性。

建议：虽然系统源目前尚能运行，但为了规避未来集群升级时的兼容性“暗雷”，强烈推荐安装更新更及时、生产特性更完备的containerd.io。

2.2 如何从软件源中进行下载

我们并不需要安装完整的 Docker Engine，只需通过 Docker 官方仓库精准提取containerd 即可。

  1. 添加 GPG 密钥与 Docker 官方源；

  2. 仅安装 containerd.io，更新索引并直接安装运行时，避免引入 Docker 引擎带来的多余后台进程。

2.3 如何修改核心配置

containerd 安装后的默认参数通常面向通用容器，而非 K8s。我们需要进行“精调”以满足生产需求。

  1. 初始化默认配置文件；

  2. 启用 SystemdCgroup 驱动。这是 K8s 集群平稳运行的关键。如果不开启，在高负载下 kubelet 可能会与 containerd 发生资源管理冲突，导致节点状态异常；

  3. 配置服务代理（可选但推荐）。为了确保节点能顺利拉取位于海外仓库的pause 镜像和业务镜像，我们需要为 containerd 进程配置环境变量代理。

  4. 重启服务以使所有配置生效，并检查版本确认安装成功。

0x03 安装 Kubernetes 组件（所有节点执行）

3.1 为什么不推荐直接使用系统源安装 K8s 组件

在 Ubuntu 默认源中，Kubernetes 组件的版本通常严重滞后且更新不及时。为了确保集群能使用到 v1.35 的稳定特性并获得即时的安全补丁，我们必须通过官方专有仓库（pkgs.k8s.io）进行精准安装。

  1. 导入官方公钥；

  2. 注入 v1.35 专属软件源；

  3. 安装并锁定版本（防止系统自动更新破坏集群稳定性）。kubelet 和 kubeadm 是所有节点的必备组件，前者负责管理容器生命周期，后者负责加入集群。kubectl仅作为管理工具，通常只需要在Master 节点或运维终端上安装。为了保持 Worker 节点的极致纯净，你可以选择在从节点上跳过 kubectl 的安装。

3.2 如何确认 K8s 组件已成功接管容器运行时

在正式初始化集群前，必须确保kubelet能够通过 CRI 接口与containerd正常通信。通过crictl 工具进行自检，是排除“节点无法就绪”故障的最快方法。

只要crictl info 输出了正确的 JSON 信息，就意味着你的节点已经打通了“任督二脉”。

0x05 安装 Cilium 网络插件（Master 节点）

5.1 为什么必须安装 CNI 网络插件？

在初始化完成后，你会发现节点状态依然是NotReady。这是因为 K8s 此时还没有打通 Pod 之间的通信隧道。Cilium 作为目前云原生社区最顶级的网络插件，利用 eBPF 技术提供了高性能的网络转发、精细的安全策略以及强大的可观测性，是目前生产环境的优选方案。

  1. 获取最新的 Cilium CLI 版本号；

  2. 下载并验证二进制包；

  3. 安装到系统路径并清理缓存
